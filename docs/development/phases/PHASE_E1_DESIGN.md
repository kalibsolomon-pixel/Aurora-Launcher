# Phase E1 design: local gameplay history foundation

This design precedes implementation. The published v1.1.0 tag and its artifacts are immutable.

## Ownership and schema

The launcher owns `launcher/gameplay-history.json` under the platform managed data root. Schema 1 contains open and closed launcher-timed sessions keyed by a random UUID: validated `InstanceId`, UTC start/end seconds, elapsed monotonic milliseconds, terminal outcome, observed gameplay mode, and bounded visits. A visit records a mode, validated target identity when known, separate optional display text, and launcher-observed start/end timestamps. A session with no bridge still records process time and an unknown mode. The raw sessions are authoritative; daily and per-instance totals are computed in bounded native queries. No frontend localStorage, account IDs, credentials, or network upload are involved.

The file has a strict schema version and strict field/length validation. There is no legacy history file, so a missing file initializes schema 1; malformed or future files fail closed and are never overwritten. Writes use a unique sibling temporary file, sync, and rename. The first write happens after spawn, then only on a meaningful activity transition and on process exit. An interrupted open session is reconciled on next load as an interrupted outcome with duration limited to the last launcher-observed checkpoint; no untrusted wall-clock gap is counted. Detailed history retains the latest 256 sessions and 16 visits per session. Older closed sessions compact into per-instance UTC daily totals, retained for ten years, with a cap of 8192 day/instance buckets. "All time" means all retained history. The raw retained sessions are authoritative for their interval; older daily totals are derived once at pruning. No old schema exists to migrate. Future schemas fail without rewrite.

## Identity and bridge

Bridge v1 keeps its exact authenticated handshake and display-only snapshots. Bridge v2 is explicitly negotiated by the launcher-owned `AURORA_ACTIVITY_PROTOCOL=2`; v2 hello/acceptance/activity frames use schemaVersion 2. The client supports both bootstrap versions. The launcher receiver implements v2, but production still selects v1 for the reviewed v2.1.3 artifact; no reviewed production artifact carries the new client code yet. Unknown client hashes do not receive a bridge. A future release must pin its reviewed hash and select v2. An old launcher presented with a new unrecognized artifact runs normal Play with process-only Discord fallback. Loopback binding, fresh session/capability, constant-time check, frame/deadline/attempt bounds, one connection, monotonic whole snapshots and nonfatal failure remain unchanged. A v1 snapshot can classify a session but never create a quick-launch target.

V2 carries `worldSaveId` only for singleplayer and `serverTarget` only for multiplayer, independently from display name/address. The client obtains the save directory component from the integrated server's storage root, not the world title. The launcher accepts only one bounded safe save-directory component: no separators, traversal, drive prefix, control/format characters, trailing dot/space, or reserved Windows names. Future use must revalidate the identity, resolve it under that instance's `saves/`, reject links/escapes, and check the world exists. A changed display title does not change identity. The multiplayer target comes from Minecraft's current ServerData connection address, not its display name. Native parsing rejects malformed hosts/ports and canonicalizes DNS/IPv4/bracketed IPv6 before storing; it does not resolve DNS. LAN/Realms without a validated stable target remain activity only.

The bridge snapshot carries separate display and validated target fields. Discord reads only display fields and keeps its existing independent Show World, Show Server, and Show Server Address controls. History is local and is never projected into Discord or generic diagnostics. Internal target fields use redacted Debug. Native query DTOs expose bounded summaries and recent display labels only; a future launch command takes an opaque history entry ID, then looks up and revalidates the native target and instance. The frontend never supplies a path, address, Java argument, or executable as launch authority.

## Quick launch and Home boundary

`QuickLaunchTarget` has only `Singleplayer { InstanceId, WorldSaveId }` and `Multiplayer { InstanceId, ServerTarget }` variants. A later phase must feed a revalidated target into the existing resolve → validate → LaunchSpec → spawn → supervision path. The local mapped Minecraft 1.21.11 client bytecode verifies `--quickPlaySingleplayer` (optional world ID value) and `--quickPlayMultiplayer` (required server address value). `QuickPlay` passes the world ID to `WorldOpenFlows.openWorld`; a blank value instead selects the most recently played world, which Aurora must never use for a specific target. Multiplayer calls `ServerAddress.parseString` and `ConnectScreen.startConnecting`; it also reads or adds the address in Minecraft's server list. `--quickPlayPath` is a separate required argument used for quick-play logging. E1 adds none of these arguments. Future Home IDs are `playtime`, `recent-worlds`, and `recent-servers`; none is registered or rendered in E1. Existing layout persistence already retains unknown IDs, and future registration must declare sizes and use the existing ordering, hide/show and reset behavior.

## Failure behavior

Invalid v2 identity is rejected rather than used as a target. Bridge loss clears the current activity and closes an open visit, while process supervision still closes the session and counts process lifetime. History I/O failure cannot change game launch or Discord; it is a native history error surfaced only by future history queries. No history failure can authorize a launch. The launcher must not modify user worlds, server list, mods, logs, or `.minecraft` while collecting history.

## Native query contract

Read-only native operations are `get_playtime_summary(instanceId?)`, `get_recent_worlds(instanceId?, limit)`, and `get_recent_servers(instanceId?, limit)`. Limits are capped natively. Summary returns today, 7-day, 30-day and all-time milliseconds in UTC buckets; recent entries return opaque IDs, instance IDs, safe display labels, last played time, and visit duration. They do not return raw persistence or internal target strings.
