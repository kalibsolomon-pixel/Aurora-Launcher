## What changed

| Area | Change |
| --- | --- |
| Instances | Installed instances are individual tile cards (icon, name, configuration, status, Selected marker). The whole tile opens the instance; Select / Retry / Validate stay separate actions. No enclosing panel, so no card-on-card nesting. |
| Icons | Each instance can have a Google **Material Symbols** icon. Creation (from scratch, not modpacks) and the instance's Settings have a picker with 18 suggested icons, search (with a small Minecraft synonym map, e.g. "tree" → forest/park) and **Browse all** (3,927 symbols, paged 240 at a time). | Modpacks | Browsing modpacks **inside an instance** adds the pack's content to that instance. The standalone browser on the Instances page still creates a new instance. |

## Icon storage and source

- Icons live in `launcher/instance-icons.json` (schema 1: `{ schemaVersion, icons: { instanceId: name } }`), **not** in the instance registry, so the registry schema and older launchers are untouched. Unknown schemas and malformed files fail deliberately and are never overwritten; writes are atomic; names are validated (`[a-z0-9_]{1,64}`); entries for removed instances are ignored and dropped on the next write.
- Glyphs come from the pinned `material-symbols@0.47.6` package (Google, Apache-2.0), self-hosted as the 4.0 MB Outlined woff2. It loads from the app origin, so the CSP and offline use are unchanged. The name list (`src/lib/instances/materialSymbolNames.ts`) is generated by `tools/icons/generate-material-symbol-names.mjs` and loaded only when the picker searches or browses.
- Icons are presentation only: a failed read leaves fallback glyphs; an icon write can never fail instance creation.

## Adding a modpack to an existing instance

`pack_merge.rs` (`preview_modrinth_pack_merge`, `install_modrinth_pack_merge`). The pack's content becomes **ordinary content** of the instance (direct, retained, removable provider records; no pack ownership), because pack-owned instances cannot contain Aurora Client by registry rule. The instance does not follow pack updates.

Rules, all decided in a read-only plan shared by preview and install (install re-plans and compares a fingerprint):

- Minecraft version must equal the instance's; the instance's Fabric Loader must be at least the pack's; non-Fabric or pack-owned instances are refused.
- Existing files are never overwritten or adopted. Byte-identical files are skipped ("already in this instance"); a differing settings override keeps the user's file ("your files kept as they are"); a differing mod file, or a different version of an installed Modrinth project, blocks the merge. An Aurora instance's protected Fabric API is kept and the pack's copy skipped.
- The preview runs the same whole-batch validation install runs (provider conflicts, pack-internal mod identities, external jars vs. the instance, projected dependency validation), so review states exactly why a pack can't be added.
- Install order: verified downloads → provider transaction (atomic, collision-checked) → external jars and overrides. On failure, only files the merge created are removed, each proven by its digest; the instance record, game tree and existing files are never touched.

## Related correctness fix

Fabric `provides` aliases are now honored by mod metadata (e.g. Fabric API provides `fabric`). Before this, any mod depending on `fabric` was reported as unsatisfied, which blocked real packs in both pack flows and ordinary installs.

## Limits for the owner

Several popular packs cannot be added (and, for most of these reasons, cannot be installed as new instances either) because of existing, deliberate launcher compatibility rules that were **not** changed here:

1. A top-level mod may duplicate another mod's bundled (jar-in-jar) module only at the same version (e.g. Adrenaline: ServerCore bundles a different `placeholder-api`). Fabric Loader itself would pick the newest.
2. Fabric Loader's own bundled MixinExtras is not counted as installed (e.g. Remarkably Optimized: AsyncParticles needs MixinExtras ≥ 0.5.0; only ModernFix's bundled 0.4.1 is seen).
3. Phase I's resolver rejects packs whose Modrinth-declared dependencies are absent from the pack snapshot, and certain override paths.

Relaxing 1–2 would change mod-compatibility authority and needs an owner decision.
