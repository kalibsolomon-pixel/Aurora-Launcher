# Proposed P3-B — owner review only

P3-B is **NOT AUTHORIZED / NOT READY**. First close frame-tool permission,
controlled presentation calibration, authenticated Minecraft validation, immutable
world/material locks, B/C compatibility and quiet-system gates. Use the separate
Windows test-user procedure. Installing a game or passing parser tests does not
authorize repeated gameplay.

Freeze each workload/hash, runtime/build/hash, capture binary/settings, clocks,
graphics/display/power and explicit heap treatment. Existing production owner settings
are not a baseline to inspect/copy without separate scope. A0 is a newly created
disposable Existing Configuration at 2048 MiB with no tuning. Java 21 defaults with
the same required Minecraft arguments/heap are the same treatment for this Fabric
baseline; use blinded A/A labels to estimate noise. Balanced and Performance advice
currently produce identical values when facts match, so collapse their equal
effective vectors rather than invent a name-based effect.

After a short authorized Minecraft capture pilot, perform instrument-on/off A/A
calibration. Future laboratory logging uses Existing Configuration with identical
GC instrumentation in every matched instrumented treatment; explicitly record
the P2 advice source and any user-approved application of its concrete recommendation.
No product validator change or hidden instrumentation in a saved preset. Keep the
uninstrumented A/A series distinct. Use the supported maximum-heap field only; no
Xms/collector/pause/worker/affinity/power changes. If live advice differs because
available RAM changed, freeze the reviewed concrete heap, do not retune each run.

Candidate comparisons after A/A: baseline/equivalent-default control, explicitly
applied Efficient heap advice (at most 1536 MiB), explicitly applied Balanced/
Performance advice (same at most 2048 MiB), and separately reviewed conservative
heap alternatives only if workload evidence justifies them. A failing/OOM baseline
remains in the denominator; a larger-heap condition gets a new ID, not a hidden fix.
No new recommendations or tuning comparison was executed in P3-A.

At least five usable independent runs per effective configuration/workload where
practical; >=300 s in-world warm-up + 600 s measurement each. Restart the exact Java
child and restore a fresh test-created snapshot for every run. Rotate predeclared
paired blocks A/B/C, B/C/A, C/A/B, C/B/A, A/C/B, then B/A/C if extended. Identical
blinded A/A labels are calibration controls, not distinct optimizations. Keep
cooldown consistent and record thermals/conditions. Only predeclared loading/warm-up
windows are excluded; never clip stutters after seeing results.

Retain raw data/digests, producer diagnostics, failed/interrupted attempts, clock
anchors, start/stop markers and manual scene deviations. Review quality before
statistics. Report per-run results, then paired run-level changes/medians/SD and
exploratory bootstrap intervals from P1 (>=5 pairs). Do not pool all frames as
independent trials, mix workloads/platforms, or treat five runs as proof of significance.

Primary: P99 frame interval and predeclared stutter events. Supporting: mean/median/
P95/P99.9 at sufficient depth, real presentation rate, GC pauses/logged-phase CPU,
working set/available memory, process CPU, startup/world-load and failures. Freeze
minimum useful effects and tolerated resource/startup regressions from A/A noise
before comparing heaps. Correlation remains observational.

Promotion requires valid Minecraft capture, locked representative workloads,
repeated benefit beyond noise, acceptable CPU/memory/startup/failure tradeoffs,
no launch/compatibility regression, held-out scene/hardware confirmation and owner
review. This document grants no P3-B execution or Performance-mode promotion.
